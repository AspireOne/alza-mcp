# Architecture

The server is a single-account research adapter around the current Alza.cz storefront and its mobile-app API. The goal is evidence that an agent can inspect: product identity, complete traversal state, prices with their conditions, and explicit failures. The storefront is an undocumented dependency, so success means validating the response's meaning, not merely receiving HTTP 200.

## Backends

Two interchangeable backends read Alza: the browser backend and the API backend. `ALZA_BACKEND` selects one per process. [Research](src/domain/research.ts) owns traversal, caching and the result contract for both; each backend supplies a [`Catalog`](src/domain/catalog.ts) that retrieves and parses data, and an `Access` that owns its sources and sign-in. The browser backend is the long-tested path and stays the fallback, so the API backend never falls back to it silently. Instead, failures that suggest an Alza-side change name the switch.

The API backend impersonates Alza's Android app: its user agent, `Balancer-Guid` visitor ID and OAuth client. These are public in the app and may change with app releases. Cloudflare rejects Node's HTTP/1.1 TLS fingerprint for app-identified requests but accepts its HTTP/2 client, so the [transport](src/infra/api-transport.ts) uses only HTTP/2 and follows redirects only within Alza's hosts. Every payload is schema-checked against the fields the adapter reads; a mismatch logs the failing paths and fails as `SCHEMA_CHANGED` rather than producing partial guesses. One transient network retry shares the operation deadline. There is no challenge solving: a bot block is `API_BLOCKED`.

The app's endpoints, request formats and enum values come from the decompiled app and live probes, not documentation. Category listings and text search take the same filter object as the app: facet values `{tId, v, vFrom, vTo}`, condition as `commodityWears` (new 0, opened 2, used 1 and 3) and in-stock-anywhere as `availabilityType` 1. Product detail combines the legacy router payload (prices, availability, parameters) with the v14 detail (brand, manuals, variant link); the v14 call needs the price-group and account context from the router's self link.

## Access and recovery

On the browser backend, a managed, persistent Patchright Chromium profile is the primary data source. Running headed under Xvfb keeps the same browser mode on the home server and in container checks. Browser, operating-system and network identity still differ from a copied desktop session; copying cookies cannot guarantee trust or prevent a challenge.

The browser executes storefront GET requests and the read-only catalogue filter POST in its own context. Page scripts may perform their normal browser traffic; the adapter exposes no transaction operations. It does not block media or replace Chromium's native user agent.

FlareSolverr is the second provider. It uses a temporary session, can receive scoped Alza cookies, and must independently verify an imported account. Byparr is the final anonymous provider. Its pinned version has no equivalent account-session import contract, so `auth=required` cannot use it. Both are private services, not proxies exposed to MCP clients. Before external recovery starts, primary contexts drain their active readers and close; admission waits behind that release, so recovery cannot tear down another request's tab. Each caller's wait still observes its own deadline and cancellation. Persistent profiles reopen on the next primary operation.

Recovery repeats a read operation through an eligible provider. A 120-second operation deadline includes queueing and cleanup. Provider budgets are capped by the remaining operation time: primary browser 30 seconds, FlareSolverr 50 seconds, Byparr 30 seconds. The browser and solver budgets accommodate full product hydration and account verification on ARM64 home servers. One transient browser request retry shares that deadline. Rate limiting, account mismatch and parser failures are not treated as reasons to hammer another provider. Failed challenge recovery starts a five-minute context-specific cooldown. No human CAPTCHA flow or paid solver is required.

Solvers can return synthetic HTTP 200 and HTML wrappers around JSON. The adapter validates challenge markers and payload schemas instead of treating the solver status as Alza's original HTTP status. Recovery renderers cannot always prove selected filter state or hydrate all lazy product sections. Such limitations are explicit errors or failed sections, never unfiltered successful results.

The dependency versions are fixed in [package-lock.json](package-lock.json), [Dockerfile](Dockerfile) and [compose.yaml](compose.yaml). Upgrade a browser package and its installed binary together; keep provider contract tests and live probes in the same change.

## Identity and state boundaries

A numeric Alza product ID identifies a listing. A product code can appear on new, opened or used listings with different IDs, so code resolution must establish a unique exact match. A canonical product request must return the requested ID before any detail is accepted.

Anonymous and imported-account profiles use separate persistent browser contexts. Concurrent startup is deduplicated per profile, and each operation owns a separate page and authentication verification state. Account identity comes from a fresh first-party page's signed-in state and numeric user ID, not from cookie presence. A requested page supplies this evidence directly; cache-only and JSON-first reads load a first-party page when the operation has not yet verified identity. Verification is scoped to the operation, so retained browser state cannot authorize a later cached response. Account replacement creates a new generation, which invalidates prior cache and traversal contexts. A filesystem lock prevents two processes from owning the same profiles. Never launch a separate browser against these managed directories. Under the exclusive lease, stale Chromium locks from a replaced container can be removed; a live local browser PID is still rejected.

The API backend's account is an OAuth session from the app's PKCE sign-in, stored in `api-session.json` with the expected account ID and a visitor ID. The access token's `sub` claim must match the expected ID at sign-in and on every refresh. Restservice responses also report `user_id`; an anonymous answer to a signed-in request is `AUTH_REQUIRED`, and another account's ID is `AUTH_ACCOUNT_MISMATCH`. Concurrent callers share one refresh, and a rotated refresh token is written to disk before use, because the old one may already be invalid. The session generation keys caches and cursors as the browser account generation does.

Session import is an offline administrative action. It validates a temporary profile before replacing the manifest. Filesystem protection matters because Chromium cookies and storage state remain credentials even when the MCP surface is read-only. Whole-profile import is an extraction path, not a promise that encrypted cookies, device-bound tokens or browser fingerprints are portable.

## Completeness and source fidelity

HTML adapters may share a parsed document only within the same HTML capture. Helpers receiving that document must treat it as read-only. A later browser capture requires a new parse, especially the final identity check after hydration; sharing a parsed tree must never become an authentication or cross-request cache.

Catalogue results use the filter response's count and paginator rather than guessing a result limit from the first page. Filters are discovered from the page bootstrap and advertised controls. Enum keys, range values, ordering and availability are sent in the storefront's own request format. Some search terms redirect to navigation-only category hubs, which cannot prove a complete product traversal. Alza renders the stock control after the initial HTML response on some listings, so a stock-filtered browser search waits briefly for that control before interpreting the page. Search results retain Alza's own relevance order.

Continuation state retains seen product/review identities and the original query, count and account context. Signed tokens reference bounded in-memory traversal state. They are replayable within the state lifetime, but cannot resume after a server restart. Count changes, repeated identities and inconsistent terminal pages produce explicit incomplete results. Offset pagination cannot detect every possible same-count edit; the API therefore never promises snapshot isolation.

Products combine structured data with rendered, lazy-loaded sections. Hydration follows the requested sections and their dependencies: specifications and downloads may require both detail tabs, while media requires the description. Product-document cache keys include hydration coverage so a prices-only capture cannot satisfy a later full-detail request. Structured price precision and displayed rounding are both retained, including upstream fractions smaller than one haléř. A listing's membership price is effective only when verified authentication and applied-membership markup agree; advertised conditional offers remain conditional. “Bez členství” is a reference within the current account context, not proof of the anonymous price. Coupon codes and totals come from catalogue coupon blocks and product-detail promotion rows, available in server HTML as well as rendered pages. JSON-LD `SalePrice` alone does not establish a coupon or identify its code. Promotion totals are observed in the current account context; the adapter does not calculate stacking. The [offer contract and comparison rules](README.md#read-results-correctly) distinguish coupons from cashback and describe their conditions. Sanitized pricing captures live in [test/fixtures](test/fixtures/README.md).

Variant-selector options preserve Alza's displayed labels and price differences; a linked numeric product ID is not invented when the selector supplies none. Reviews use the paginated review endpoint, not the SEO sample. Review statistics require context parameters from the actual product page. Product ratings, reliability and review statistics share the same cached upstream response; its self link must identify the requested listing before it is accepted. Each dependent section validates its own fields, so malformed complaint data can fail reliability while preserving valid ratings. Reliability is read from that structured endpoint rather than inferred from HTML colours. The [rating and reliability contracts](README.md#read-results-correctly) describe their source scopes, units and limitations.

Search and product caches last 60 seconds, reviews five minutes, and category data 24 hours. Keys include account generation and provider. Caches are bounded and private to the process; an anonymous operation cannot reuse an account price. This short lifetime reduces repeat traffic without pretending prices are immutable.

## Concurrency, transport and observability

The access queue admits at most two operations by default; `ALZA_BROWSER_CONCURRENCY=1` restores serial admission. Eight additional operations may wait, each bounded by its original operation deadline. Requests use separate pages. Page creation and interactive detail hydration share a serial gate so a new tab or another control interaction cannot interrupt a detail snapshot; navigation and browser JSON reads can overlap. Interactive waits also respect the primary provider budget. A full access queue returns `BUSY`; a waiting operation that reaches its deadline returns `TIMEOUT`. Shutdown drains active work and closes every context before releasing the profile lock.

Idle browser eviction belongs to the access coordinator because queued operations and solver recovery must also prevent eviction. It uses the same coordinated browser-close path as recovery: new readers wait for closure before reopening persistent profiles. Eviction retains the application lease, account generation, caches and continuation state; it is not an application restart. See [idle timeout configuration](README.md#configuration-and-local-development).

Stdio and HTTP share the same research service. HTTP creates an MCP protocol instance per request; JSON-RPC IDs belong to that request, not to a global namespace. Stateless cancellation notifications cannot reliably identify an active call and do not cancel it. It validates Host and Origin, authenticates each request, and limits request bodies. In `token` mode it checks a static bearer secret. In `cloudflare-access` mode it verifies Cloudflare's RS256 assertion against the team JWKS, exact issuer and app audience, expiry, token type, and allowed email. The modes are exclusive: a static bearer secret cannot bypass Access. Cloudflare Access handles OAuth discovery and user sign-in at the edge; the origin does not issue OAuth tokens. A socket disconnect does not implicitly cancel a read that may already be running.

Tool-level validation and upstream failures share the [result contract](src/domain/contracts.ts). Each tool advertises an [output schema](src/domain/outputs.ts) that the compiler checks against these types, and the server validates every result against it. A result that breaks its schema is a protocol error, not a mistyped success. Section data whose shape differs by backend stays untyped. Protocol-level malformed JSON and unknown tools remain transport/protocol errors. Text content contains the same complete JSON as structured content, so clients without structured-output rendering do not receive a shortened success story.

Logs record request IDs, providers, durations and failure codes. Raw browser messages, cookies, HTML and imported storage are not logged. Health checks inspect only the local process; recovery and last-failure state are available through `get_session_status`.

The adapters own upstream interpretation; the research service owns traversal and cache context; the access coordinator owns browser/provider lifetimes, and `ApiAccess` owns the app session and transport. Changes should stay at the boundary that owns the failure. Avoid creating a generic scraping framework until another actual source needs one.
